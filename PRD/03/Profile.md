# PRD Profile Information UI/UX  

**هدف:** طراحی فرم ثبت و ویرایش اطلاعات  کاربر برای استفاده در رزرو/پرواز/تور

---

## 1. هدف و دامنه محصول
این صفحه برای ثبت و مدیریت اطلاعات پایه کاربر طراحی می‌شود تا در سناریوهایی مانند رزرو بلیت، صدور فاکتور، صدور بلیت خارجی استفاده شود.

### 1.1 اهداف اصلی
- دریافت اطلاعات پایه کاربر به‌صورت شفاف و قابل فهم
- پشتیبانی از کاربران **ایرانی** و **غیر ایرانی**
- تفکیک واضح اطلاعاتی که ممکن است برای کاربران مختلف متفاوت باشد
- کاهش خطای ورود اطلاعات با استفاده از راهنمایی‌های UX و Validation

### 1.2 اصول طراحی
- فرم باید ساده، قابل فهم و کم‌خطا باشد
- فیلدهای مرتبط باید در گروه‌های منطقی دسته‌بندی شوند.
- تفاوت بین فیلدهای مشابه باید با متن راهنما و UI شفاف شود
- در مواردی که اطلاعات بر اساس ملیت متفاوت است، UI باید این تفاوت را به‌صورت واضح نمایش دهد

---

## 2. اطلاعات مورد نیاز کاربر
فرم باید اطلاعات زیر را از کاربر دریافت کند:

- نام
- نام خانوادگی
- کد ملی
- جنسیت
- تاریخ تولد
- ملیت
- کشور
- شماره پاسپورت
- تاریخ انقضای پاسپورت
- ایمیل

---

## 3. نیازمندی‌های عملکردی
### 3.1 اطلاعات هویتی (Identity Information)
- فرم باید فیلدهای **نام** و **نام خانوادگی** را به‌صورت Text Input دریافت کند.
- فیلد **جنسیت** باید فقط شامل دو گزینه باشد:
 - مرد
  - زن
- فیلد **کد ملی**:
 - این فیلد **فقط برای کاربران ایرانی** نمایش داده می‌شود.
 - اگر ملیت «ایرانی» انتخاب شود، این فیلد باید در فرم ظاهر شود.
 - اگر ملیت «غیر ایرانی» انتخاب شود، این فیلد باید **مخفی (Hide)** شود.
- فیلد **تاریخ تولد** باید بر اساس ملیت کاربر نمایش و دریافت شود:
  - برای کاربران **ایرانی**: تاریخ **شمسی**
  - برای کاربران **غیر ایرانی**: تاریخ **میلادی**
- نحوه نمایش تاریخ تولد باید برای کاربر کاملاً شفاف باشد و فرمت تاریخ در UI مشخص شود.

### 3.2 ملیت و کشور (Nationality / Country)
- فیلد **ملیت** باید به‌صورت **لیست بازشونده (Dropdown)** طراحی شود.
- کاربر باید بتواند ملیت خود را از لیست انتخاب کند.
- در UI باید به‌وضوح مشخص باشد که این فیلد قابل انتخاب از لیست است.
- در طراحی این بخش باید سناریوی **ایرانی / غیر ایرانی** در نظر گرفته شود.
- در صورت نیاز، بعد از انتخاب ملیت، سایر فیلدهای وابسته می‌توانند بر اساس آن رفتار متفاوت داشته باشند.

### 3.3 شماره پاسپورت (Passport Number)
- فرم باید فیلد **شماره پاسپورت** را دریافت کند.
- این فیلد برای پروازهای خارجی ضروری است.
- ورودی این فیلد باید به شکلی باشد که کاربر تشخیص دهد منظور شماره پاسپورت است.

### 3.4 تاریخ انقضای پاسپورت 
- فرم باید **تاریخ انقضای پاسپورت**  را دریافت کند.
- تاریخ باید **به‌صورت میلادی** دریافت شود.
- نحوه نمایش و انتخاب تاریخ باید برای کاربر واضح  باشد.

### 3.5 ایمیل (Email)
- فرم باید فیلد **ایمیل** را دریافت کند.
- این UI باید به‌گونه‌ای باشد که کاربر متوجه شود این فیلد مخصوص ایمیل است.
- فیلد باید دارای **Validation فرمت ایمیل** باشد.
- در صورت وارد شدن فرمت اشتباه، پیام خطا باید واضح و قابل فهم باشد.

---

## 4. نیازمندی‌های UX و رفتار فرم
### 4.1 ساختار کلی فرم
- فرم باید به بخش‌های مجزا تقسیم شود:
  - اطلاعات پایه
  - اطلاعات سفر و هویت
- این دسته‌بندی باعث کاهش شلوغی و افزایش خوانایی می‌شود.

### 4.2 نمایش وابسته به ملیت
- **ملیت ایرانی:**
    - نمایش فیلد **کد ملی** (الزامی).
    - نمایش تقویم با فرمت **شمسی** برای تاریخ تولد.
- **ملیت غیر ایرانی:**
    - **مخفی کردن فیلد کد ملی** (این گزینه نباید برای مسافر خارجی نمایش داده شود).
    - نمایش تقویم با فرمت **میلادی** برای تاریخ تولد.
- این تغییر وضعیت (نمایش/مخفی) باید به صورت آنی (Real-time) پس از انتخاب ملیت در فرم اعمال شود.

### 4.3  ملیت
- فیلد ملیت باید حتماً **لیست بازشونده** داشته باشد.
- کاربر باید بتواند گزینه مورد نظر را انتخاب کند.
- در صورت زیاد بودن گزینه‌ها، قابلیت جستجو در لیست پیشنهاد می‌شود.

### 4.4 اعتبارسنجی
- فیلد ایمیل باید validation داشته باشد.
- فیلدهای تاریخ باید فرمت قابل قبول داشته باشند.
- فیلد شماره پاسپورت باید از نظر طول و ساختار بررسی شود.
- در صورت انتخاب ملیت نامعتبر یا عدم تکمیل فیلدهای ضروری، پیام خطا باید مشخص باشد.
